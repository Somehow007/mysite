把博客变成可以被提问的知识库：一次 pgvector + 意图路由的实践

从 Markdown 感知分块到熔断式多模型路由，我把这几个月踩过的坑写成一份可复用的清单——以及为什么最后决定“意图只判断模式，不替用户选择知识库”。

某某2026 年 11 月 12 日 · 12 分钟 · 2.3k 阅读

这个站点最初只是一个普通的博客。直到有一天我发现，自己回头查“上次 JWT 刷新是怎么处理的”时，翻目录的时间比重新想一遍还长。于是我决定：让博客自己回答关于它的问题。

这篇文章记录整个 RAG 子系统的设计取舍。它不是教程，更像一份工程日志——哪些地方我一开始想错了，最后又是怎么改回来的。

§ 01为什么不直接用 Elasticsearch

站内已经有 ES 做关键词搜索，并且可以关掉回退到 DB LIKE。但关键词搜索解决的是“找到那篇文章”，而我想要的是“直接得到答案”。语义召回 + 生成，是两个完全不同的问题✦ 问 AI 这段引用复制，混在一个引擎里只会两头都做不好。

TL;DR关键词检索留给 ES，语义检索放进独立的 PostgreSQL + pgvector，两个数据源互不混用。

§ 02分块：尊重 Markdown 的结构

按固定长度切文本最简单，但会把代码块从中间劈开、把标题和它的内容分到两个 chunk 里。MarkdownChunker 先按标题建树，再在叶子节点里按 800 字切分，保留 100 字重叠。

JAVA · MarkdownChunker.java复制
public List<Chunk> chunk(String markdown) {
    // 代码块、列表视为不可分割单元
    var blocks = parser.parseBlocks(markdown);
    return splitter.split(blocks, 800, 100)
                   .limit(MAX_CHUNKS).toList();
}
好的分块不是切得均匀，而是切完之后每一块都还能独立被读懂。

§ 03意图路由：只判断模式

早期版本里，意图分类器会顺手“帮用户”挑知识库。结果是它经常挑错，而用户完全不知道为什么回答变了味。现在分类只输出三种模式：

  • KB_RETRIEVAL：走检索，范围由用户选定的知识库决定
  • CHAT：纯对话，跳过检索
  • MCP：工具调用（预留）

§ 04多模型路由与熔断

连续 2 次失败后打开熔断，首次成功即重置冷却。关键约束是：只允许在首个 token 之前切换 provider，否则用户会看到一条由两个模型拼起来的回答。
